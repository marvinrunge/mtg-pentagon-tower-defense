- 2026-08-24: Fixed melees unable to damage the crystal (and, downstream, the "enemies stand there instead of attacking" symptom near it). That's why a single enemy in isolation could still attack (matching an earlier synthetic single-enemy test that found no bug at all) while real multi-lane convergence broke it: every lane's melee funnels to the exact same single boundary point and physically jostles neighbors there, and 0.13 units of margin doesn't survive that. Re-verified: closest navmesh point is now directly under the anchor's own XZ position, margin widened from 0.13 to **1.5 units**. - 2026-08-24: Fixed ranged/mage projectiles occasionally never disappearing - a DIFFERENT race from the pool-exhaustion one fixed earlier the same day, on the completely normal non-exhausted path. `scripts/projectile.gd`'s `deactivate()` set `active=false` synchronously but deferred `process_mode=DISABLED` via a blind `set_deferred(...)` (needed because `deactivate()` runs from the `_on_body_entered` physics callback, where disabling collision synchronously is unsafe). If a DIFFERENT caster calls `ProjectilePool.get_projectile()` and reactivates that same now-`active=false` slot **later in the same physics frame** (routine once several Ranged/Mage enemies plus the player fire regularly against a `projectile_pool_size` of only 20), the reused projectile's synchronous `activate()` sets `process_mode=INHERIT` - and then the FIRST projectile's stale deferred call fires at end-of-frame and disables it anyway, freezing the reused projectile in place forever (`active=true`, `visible=true`, `_physics_process` never runs again so `life_timer` never expires). Reproduced deterministically headless (`get_projectile()`→`activate()`→`deactivate()`→`get_projectile()` again→`activate()`, no `await` in between, matching a same-tick hit-and-refire) and confirmed the frozen end-state exactly. Fixed by deferring a re-checked call instead of a blind property set: `call_deferred("_finish_deactivate")` where `_finish_deactivate()` only sets `process_mode=DISABLED` if `active` is *still* false by the time it runs - preserves the original "don't touch physics state synchronously in a collision callback" safety property while becoming immune to same-frame reuse. General lesson: `set_deferred(prop, value)` on an object that might get reused/reset before the deferred write actually applies is itself a footgun (this is the second distinct bug from this exact pattern in this file in one day) - prefer deferring a method that re-validates state at execution time over deferring a raw property write.
- 2026-08-24: Fixed Myrs getting stuck at the mana well. `scripts/myr.gd`'s `HARVESTING`/`DEPOSITING` states zeroed `velocity.x`/`velocity.z` and ran their timers but never called `move_and_slide()` - the only thing that actually applies `velocity` and refreshes `is_on_floor()`. Since gravity is integrated into `velocity.y` unconditionally every physics frame regardless of state, `velocity.y` fell unbounded for the whole `harvest_time`/`deposit_time` (verified: would reach roughly `-gravity * duration`, e.g. ~-29.4 for the 3s harvest) with nothing ever consuming it. The next `move_and_slide()` call (once the state timer expired) then had to resolve several seconds of pent-up fall speed in a single slide, plausibly jamming the Myr into the well's collision instead of walking off. `scripts/enemy_base.gd` already avoids this class of bug by calling `move_and_slide()` unconditionally in every branch of its physics loop, including while frozen/stunned/mid-attack; `myr.gd` just didn't follow that pattern for its own stationary states. Fix: added `move_and_slide()` to both branches. Verified by forcing a Myr directly into `HARVESTING` (bypassing navigation, which needs a baked navmesh a synthetic test scene doesn't have) and confirming `velocity.y` now stays bounded to a single frame's worth of gravity rather than growing across the whole harvest duration, with a correct on-time transition to `WALKING_TO_CRYSTAL` while still grounded.
- 2026-08-24: Fixed bosses visibly floating (feet ~40-50% of body height above the ground while walking) - reported right after the initial boss build. Root cause: `tools/boss_character_builder.gd`'s height normalization (`_normalize_to_target_height`) is calibrated against the MESH's static bind-pose vertex AABB, but once the "walk" clip plays, its Hips POSITION track completely overrides the root bone's position with an absolute value that has nothing to do with that bind pose - confirmed this is a Mixamo-export quirk, not a cross-file mismatch: even fire_giant's OWN embedded clip (exported from the SAME fbx as its OWN mesh) has its Hips position track sitting ~10x higher than that same skeleton's own `get_bone_rest()` Y. Since only Hips carries a position track (every other bone is rotation-only) and it's applied absolutely, this single bad value lifts the entire animated character uniformly - explaining a large, consistent float rather than deformation. Fixed with a per-boss "grounding" pass (`_ground_correct_library`): for every clip, scrub it across its own length on the boss's OWN (already height-normalized) skeleton, find the lowest either foot bone (`mixamorig_LeftToeBase`/`RightToeBase`) reaches, and shift that clip's entire Hips Y track by a single constant so the lowest point touches y=0. Because every clip in a set is borrowed from a different source file (see the set-sharing note below), this can't be computed once per set - it's now computed and saved per BOSS (`lib_<boss_name>.tres`, replacing the earlier per-set `lib_<set_name>.tres` files, which are now stale and were deleted).
  - **Sharp edge worth repeating: don't forget to convert between coordinate scales when composing a correction.** The measurement (`_measure_min_foot_height`) reads bone poses through `root.transform` on purpose, so it naturally returns a WORLD-scale value (post the ~85x normalization factor) - but the Hips position track it needs to correct lives in RAW, pre-scale units. First attempt applied the WORLD-scale correction directly to the RAW track, producing a ~85x-too-large shift (bosses ended up at y≈-70 instead of y≈0). Fix: divide the measured correction by `root.transform.basis.get_scale().y` before applying it to the raw track. Caught immediately by re-running the same verification test after the fix, rather than assuming a plausible-looking code change worked - the numbers before (`-78.27`) vs after (`0.05`) were dramatically different, not a subtle miss.
  - **Sharp edge: the live editor's resource cache can serve a stale GDScript body even to a fresh `ResourceLoader.load(path, "", CACHE_MODE_REPLACE)` call**, for a script that's been loaded, executed, AND edited-on-disk multiple times already within one very long editor session (this file had been through several execute_editor_script rebuild cycles already today, unlike the melee builder's single same-session edit yesterday where CACHE_MODE_REPLACE worked fine). Confirmed via `.get_source_code().find(...)` on the "reloaded" resource coming back empty for a string that was definitely on disk (verified by reading the raw file separately). Worked around by reading the file with `FileAccess` directly and compiling it into a throwaway `GDScript.new()` (`source_code = ...; reload(true)`) instead of trusting `ResourceLoader` at all - but a script declaring `class_name X` then collides with the ALREADY-REGISTERED global class table entry ("Class X hides a global script class", `reload()` returns error 43) unless the `class_name X` line is stripped from the source text first (the throwaway script doesn't need global registration - the caller already holds a direct reference to it). This is a strictly more reliable pattern than `ResourceLoader.load(..., CACHE_MODE_REPLACE)` for re-running an edited tool script inside a long-lived editor session; reach for it directly next time instead of debugging cache staleness first.
- 2026-08-24: Added the five colour bosses (fire giant/Red, frost giant/Blue, treant/Green, white paladin/White, zombie lord/Black) from Mixamo-rigged Meshy meshes. Facts worth keeping:
  - **All boss rigs and clips use `mixamorig_*` bone names** (Godot's FBX importer with `fbx/naming_version=2` rewrites Mixamo's `mixamorig:Hips` to `mixamorig_Hips`), and verified every bone named by a set's clips exists on the meshes using it. That makes clips **freely interchangeable across all five rigs** despite differing bone counts (41 without fingers / 57 with / 65 for the treant) - a clip that animates fewer bones just leaves the rest at their mesh rest pose. This is what lets `standing_melee` serve both giants, and lets the two sets that ship incomplete spreads borrow from `boss/common/` (the standing-melee pack has no death clip; the mutant pack has no hit reaction).
  - **These large rest-pose deltas are NOT the elf problem and must NOT be "corrected".** Comparing an animation-only FBX's rest against its mesh's rest shows 50-88 degrees of difference, which looks alarming next to the elf incident below. It is benign here: Mixamo's without-skin exports import their rest as roughly the first animation frame, not a bind pose, and Godot's skeleton tracks set bone rotation absolutely - so the *source* clip's rest is irrelevant and only the *mesh's* bind pose matters, which is standard T-pose on all five. The elf needed retargeting because the elf **mesh's own bind pose** was anomalous. Rule of thumb: retarget against the target mesh's rest, never against an anim-only FBX's rest.
  - **These rigs import ~0.02 units tall and centred on the origin**, not standing on it (Mixamo centimetres through the importer's own conversion). `tools/boss_character_builder.gd` measures the bind-pose AABB and bakes a per-boss scale + y-lift into the visual root so every boss scene is exactly 1.7 units tall with feet at y=0 - matching the 1.7-tall collision box in `scenes/enemy.tscn`. Verified all five come out at height=1.7000, min_y=0.0000. Per-boss size then comes only from `EnemyData.model_scale` (`BossDatabase.MODEL_SCALES`), so one number drives both physical size and, via `GameSettings.get_boss_anim_speed()`, how slowly the boss animates.
  - **Mixamo bakes forward travel into the Hips track** - the boss walk clips drift up to 1.5 body-lengths and the sword-and-shield attack/slash nearly 3. Since enemies are navigation-driven `CharacterBody3D`s, all boss clips get horizontal root motion stripped (vertical kept, so the treant's leap still hops), same treatment `hit_reaction` already needed in the melee builder.
  - **Enemies in this project face +Z, not Godot's usual -Z** (they turn with `rotation.y = atan2(direction.x, direction.z)`, which points the +Z basis axis at the target). The cone `AttackIndicator` and the cone hit test both had to be built around +Z; using -Z draws every cone out of the boss's back.
  - `AnimationPlayer.play(name, -1, speed)`'s third argument does **not** show up in `AnimationPlayer.speed_scale` (which stays 1.0) - read `get_playing_speed()` instead. Cost a wrong "death speed is 1.0" reading before being caught.
  - Boss specials deliberately never target the crystal: it can't dodge and isn't in the hit set, so allowing it would burn the cooldown on a guaranteed whiff. Verified by test that `_is_special_active` never becomes true against a non-player/myr target.
